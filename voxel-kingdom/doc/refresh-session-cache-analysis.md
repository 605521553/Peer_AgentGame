# 刷新后的登录恢复与场景缓存分析

日期：2026-10-15。范围：仅分析当前实现与建议，本次不修改游戏代码、不部署。

## 结论

自动恢复登录难度低；保存视角难度低；IndexedDB 场景缓存与按版本补同步难度中等。刷新后浏览器会重新启动 Godot/WebAssembly 和创建图形资源，本地缓存能减少下载、等待和部分计算，但不能保留已被页面刷新销毁的引擎实例或 GPU 场景。

推荐按顺序实现：自动恢复身份和视角；消除重复全量快照并按实体版本更新渲染；持久化场景快照及模型数据；新增受限的增量恢复协议与全量回退。服务端始终是世界状态的权威来源。

## 当前代码事实

核对文件：`web/app.js`、`web/shell.html`、`scripts/main.gd`、`backend/app.py`、`backend/store.py`、`backend/models.py`、`deploy/nginx-ip.conf`。

| 数据 | 当前所在位置 | 刷新后 |
|---|---|---|
| token、player_id、world_id | localStorage，按房间保存 | 同源且存储未清除时保留 |
| 上次房间名 | localStorage | 保留 |
| 邀请码 | 输入框；不持久化 | 清空，但有效会话恢复本来不需要邀请码 |
| 建筑、体素模型、玩家列表、seq | JS 和 Godot 内存 | 丢失，重新从服务器获取 |
| mesh_cache、cell_cache | Godot 内存 | 丢失 |
| 相机位置/缩放/方向、选中目标 | 运行内存 | 未实现持久恢复 |
| WASM / PCK / JS 静态文件 | 普通浏览器 HTTP 缓存机制 | 可能复用或条件验证，不等同于世界数据缓存 |
| 世界与会话权威状态 | 服务器 SQLite | 浏览器刷新不影响 |

启动代码无条件打开加入对话框，未自动调用恢复接口。邀请码输入框只依据服务器是否启用邀请显示，没有区分“新玩家”与“有旧 token 的玩家”。因此视觉上会再次要求登录。`join()` 实际读取该房间本地 token，存在时发送 token；后端仅在没有 token 时验证邀请码。

同一浏览器、同一来源、相同房间且有效 token 存在时，按现有代码直接点击进入应可恢复，不必填写邀请码。用户所见“必须重填”的具体原因仍需浏览器请求与存储诊断，不能仅从代码断定。换协议、IP、域名或端口会切换存储来源；无痕模式、清理站点数据、无效会话或房间变化也可能影响恢复。之前验收覆盖“刷新后点击进入”，没有覆盖“刷新自动进入”，属于验收范围缺口。

当前刷新流程：页面重建 → Godot 启动、生成基础地面和相机 → 显示加入框 → 手动点击进入 → `/api/join` 返回完整快照 → 建立 WSS → WSS 再发送完整快照 → 之后按事件 seq 更新。

这意味着进入时世界数据通常完整传送两次。Godot 接到 snapshot 会将其中所有实体重新放入构建队列，未比较未变实体的 revision。已有内存模型缓存可以避免部分重复网格计算，但仍有节点重建；页面刷新后该缓存本身也消失。

## 三类缓存应分别处理

1. 静态资源：WASM、PCK、JS、纹理等，使用 HTTP 缓存和版本标识。浏览器缓存命中后仍需要初始化引擎。现有无指纹文件名不宜直接设置一年 immutable，否则更新可能长期滞留。
2. 世界数据：IndexedDB 存储房间快照、实体版本、模型内容、同步序号；适合较大的异步结构化数据。不要把完整体素世界反复 JSON.stringify 到同步 localStorage。
3. 渲染结果：GPU 节点与缓冲刷新必然重新创建。持久化 CPU 网格数据可作为后续优化，需要模型 hash、网格算法版本和渲染格式版本匹配；暂不作为第一步。

缓存不是唯一存档：浏览器可能清理存储，首次访问或缓存损坏时必须仍能从服务端完整恢复。

## 方案比较与建议

| 方案 | 优点 | 代价 | 本项目适用性 |
|---|---|---|---|
| 自动会话恢复 + 首次全量 + 在线增量 | 简单、状态正确性容易保障 | 首屏需要等完整世界数据 | 先解决当前体验缺陷，值得立即做 |
| 本地预览 + 服务端完整快照校准 | 可更早显示已有建筑；开发量适中 | 数据仍全量下载，不能称为网络增量 | 可作为缓存的过渡版本 |
| 本地快照/模型缓存 + 服务端差量同步 | 减少重复体素传输，弱网重复进入更快 | 需要版本、缺失资产、删除、回退与一致性处理 | 推荐的后续目标 |
| 进一步持久化网格 | 减少体素网格重算 | 存储开销和升级失效逻辑复杂 | 先测量网格构建瓶颈，再决定 |

工程上，游戏常用“初次基线快照 + 运行时增量”，网页应用常用静态资源缓存和会话恢复。跨刷新缓存可变世界并非每个实时游戏都采用。对于本项目这种建筑较静态、体素模型较大且频繁编辑的玩法，缓存模型和实体版本具有较高价值；这是基于项目数据特征的方案判断，并非宣称某方案在所有游戏中更普遍。

## 推荐恢复流程

读取上次身份和房间 → 并行初始化引擎、读取本地快照、向服务器验证会话 → 有缓存时显示上次场景及视角并标注正在同步 → 服务端返回新增/修改/删除内容和缺失模型 → 只应用差异 → 同步完成后允许建筑操作。

无缓存时使用完整快照；鉴权失败才显示登录框；网络错误保留缓存预览和重试状态，不把网络故障误当成身份失效。本阶段不支持离线修改或离线命令补交。

建议采用实体清单同步作为持久缓存的第一版：客户端提供已知同步序号和模型 hash，服务器返回当前实体清单及缺失模型；客户端按 entity id/revision 增删改。房间目前最多 64 栋，实体元数据清单较小，大体素模型才是重点节省对象。这比从任意久远时间回放全部事件更容易控制。

后续如支持事件补发，可复用已有 seq 和 SQLite events 表，但当前服务器没有实现按 last_seq 的恢复接口。必须定义事件保留窗口；过旧缓存、序号断层、数据库恢复或世界重置后退回全量快照。初始补发与进入实时订阅必须在同一个一致性边界内完成，避免漏掉两者之间的事件。

必要约束：

- 缓存按服务器来源、房间与身份隔离，保存 schema_version / rules_version / 世界世代标识，避免恢复数据库后旧 seq 被误判为最新。
- 快照、模型引用和 last_seq 原子提交；不能先保存新序号，再漏存对应模型。
- 使用现有模型内容 hash 和实体 revision 做去重；必须同步删除，不能只处理新增。
- 缓存损坏、缺模型、版本不兼容、存储配额不足时，可丢弃缓存并回退完整恢复。
- 服务端只接受命令，不接受客户端缓存作为权威世界；本地被篡改不会改变服务器建筑权限。
- 同步后保留未变化建筑节点，只构建新增或变化的模型；不会再次清空重建整个视图。

## 难度与验证

| 工作 | 难度 | 关键验收 |
|---|---|---|
| 自动恢复身份 | 低 | 刷新无登录框、不重填邀请码、不新占玩家槽位；无效 token 正确回退 |
| 视角恢复 | 低 | 相机位置、方向、缩放保持，房间隔离 |
| 消除重复快照和无效重建 | 低至中 | 初次同步无缺失事件，未变节点不重建 |
| IndexedDB 持久缓存 | 中 | 刷新可先显示缓存，禁用/清理存储仍可正常进入 |
| 差量恢复协议 | 中 | 离线期间增删改、模型缺失、重置、断线均一致 |
| 网格持久化 | 中至高 | 算法升级失效、显存重建正确，实际性能收益可测 |

实施前后应记录：刷新到可见场景耗时、刷新到可操作耗时、静态与世界数据下载字节数、模型重新构建数量。不能只以“浏览器已有缓存”推断性能必然提升。

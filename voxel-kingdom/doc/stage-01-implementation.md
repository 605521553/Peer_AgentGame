# 第一阶段：技术实施计划

> 版本：0.2 · 日期：2026-10-13 · 状态：已实施，验收结果见完成报告  
> 对应：[第一阶段玩法与验证](stage-01-gameplay.md) · 基线：[完整技术文档](technical-overview.md) · [完成与验收报告](stage-01-completion-report.md)

## 1. 本阶段交付

交付 Godot Compatibility 体素客户端、带聊天的 Web 页面、Python 权威建筑与 DeepSeek 服务、规则配置、模型格式与检查样例，以及双浏览器联机验证记录。

本阶段不实现移动单位、寻路、攻击、资源、施工、迷雾或完整 RTS 模拟。DeepSeek 实际调用需要在部署时提供 API Key；开发可以用固定响应推进，但真实 DeepSeek 与公网 Web 流程必须通过后才完成验收。

| `WorldView` | 地图、玩家区域、实体与资产缓存、增量应用 | G02、G08、G09 |
| 网页聊天与桥接 | 输入、调用状态、结果记录，与 Godot 交换选择信息 | G01、G10、G11 |
| `DeepSeekGateway` | 每次组装完整规则、上下文、JSON 输出解析与一次纠错 | G02、G10、G11 |

后端建议 Python + FastAPI + SQLite；单进程房间队列起步，DeepSeek 网络调用异步执行并设超时，不能占住房间执行锁。WebSocket 用于房间事件和状态更新。[FastAPI WebSocket 文档](https://fastapi.tiangolo.com/advanced/websockets/)

## 3. 第一步：切换 Compatibility

当前配置为 `Forward Plus` 和 `rendering_device/driver.windows="d3d12"`。实施时通过编辑器右上角渲染器菜单切换为 Compatibility 并保存，或修改以下配置；该配置切换已实施，实际启动验证见完成报告。

```ini
[application]
config/features=PackedStringArray("4.7", "GL Compatibility")

[rendering]
renderer/rendering_method="gl_compatibility"
renderer/rendering_method.mobile="gl_compatibility"
```

配置片段只展示相关项；保留名称、图标等其他现有配置。移除原先显式 D3D12 RenderingDevice 驱动设置，避免保留误导性的旧配置。切换后重新打开项目，确认实际渲染方法，并使用匹配实际引擎版本的 Web 导出模板。[Godot 项目设置](https://docs.godotengine.org/en/stable/classes/class_projectsettings.html#class-projectsettings-property-rendering-renderer-rendering-method)

建立一个测试场景：平面网格、四色体素建筑、基础光源、相机与方向标识。先验证桌面和单线程 Web 都能打开，再进入后续开发。

## 4. 相机、选取与网页界面

实现倾斜俯视正交相机，限制缩放与俯仰，防止进入地下或完全丢失地图。输入在聊天获得焦点时不触发地图快捷键。缩放围绕当前观察点，地图边界可见。

地面使用简单碰撞拾取网格；建筑先用包围盒筛候选，再用体素射线确定可见实心方块，支持获取局部坐标以修改指定方块。选中上下文包含实体 ID、修订号、位置与所选方块。

建议使用自定义 Godot Web HTML 外壳，将聊天和游戏画面放在同页。通过 JavaScriptBridge 交换选中位置、对象和连接状态；页面聊天请求交给后端，不能把 DeepSeek Key 放入 JavaScript。聊天面板与 Godot 客户端共享同一个玩家认证上下文。

## 5. 规则配置与初始限制

以下是初版建议值，不是引擎固有限制。先用基准场景验证，调整后统一更新配置与规则版本；玩家文档不重复维护一套数字。

| 项目 | 初始提案 |
| --- | --- |
| 房间人数 | 2–4 人；第一轮验收至少两位独立玩家 |
| 地图 | 128 × 128 地面网格，表面 Y=1；四个 64 × 64 建造区域 |
| 建筑位置 | X/Z 整数，Y 固定为 1；旋转后整个占地必须在所属区域内 |
| 单模型尺寸 | 每轴 1–32，最大包围盒体积 32³ |
| 单模型实心体素 | 1–8,192 |
| 单模型未合并外露四边形 | 不超过 16,384；按完整模型计算，不扣除地面接触面 |
| 每玩家活跃建筑 | 最多 16 栋；房间最多 64 栋，且同时满足总体预算 |
| 房间总体预算 | 实心体素不超过 131,072；未合并外露四边形总和不超过 65,536 |
| 颜色 | 任意合法不透明 RGB；调色板最多 8,192 项，逐方块独立引用 |
| `cells_v1` | 最多 8,192 条，不允许重复坐标 |
| `box_ops_v1` | 最多 1,024 个操作；操作中每个坐标均须合法；累计访问单元上限 1,048,576 |
| 请求大小 | 解压后的单命令 JSON 不超过 1 MiB；展开前先检查尺寸与操作预算 |
| 单轮 AI 输出 | 最多一项世界修改；目标缺失时澄清 |

占地按旋转后的整盒地面投影预留。底层至少有一个实心方块接触平地；不校验真实结构承重。检查总体额度时，模型更新先扣除旧实例额度，再加入新实例；失败则保留全部旧状态。

复杂度不能只看压缩文件大小或方块数。数百次对大盒填充可能消耗大量 CPU，因此累计展开操作量也要受限。大量异色或稀疏方块可能不满足面预算，即使尺寸合规也需要拒绝并解释。

## 6. 体素与颜色实现

采用完整技术文档中的 `cells_v1` 和 `box_ops_v1`。后端先展开和规范化，再下发规范数据；客户端只读取权威结果，不承担决定是否合法的职责。

网格使用 ArrayMesh，添加面顶点颜色并开启共享材质的顶点颜色作为基础色。每个面的顶点保持同一个方块色值，颜色边界拆分顶点；确保 sRGB 转换与材质乘色不会导致二次转换或错误变暗。提供无光照颜色检查模式与带基础光照的常规模式。[Godot BaseMaterial3D 顶点颜色](https://docs.godotengine.org/en/stable/classes/class_basematerial3d.html#class-basematerial3d-property-vertex-color-use-as-albedo)

先完成暴露面剔除，再加入同色 Greedy Meshing。单建筑局部分块可先用 16³；块边界查询相邻数据，避免多出内部面或缺面。构建和 GPU 提交分帧排队，同一实体的新修订到达时丢弃过时任务，不能让旧模型晚完成后覆盖新颜色。

准备五类固定蓝图：均色实心块、空心门洞建筑、相邻异色、每方块不同色、稀疏或棋盘格。RGB 是真实数据，不能以调色板量化换取验收通过。

## 7. 命令与 DeepSeek 接入

| 命令 | 服务端行为 |
| --- | --- |
| `world.query` / `entity.query` / `rules.query` | 查询当前阶段允许的信息，不修改状态 |
| `building.create` | 绑定当前玩家归属，校验蓝图与位置后创建实例 |
| `building.update_model` | 检查归属和修订号，以新模型原子替换；本阶段不改变位置与朝向 |
| `building.demolish` | 检查己方归属后移除，释放占地与额度 |
| `building.destroy` | 检查己方归属后记录销毁事件，移除活跃实例并释放占地 |

网关根据认证会话取得身份和房间，读取最新规则与所选实体。修改原建筑时，向模型附带该建筑的规范蓝图；过大上下文则明确告知无法完成本轮生成，不静默丢掉重要模型数据。

每次 DeepSeek HTTP 调用都包含完整规则包与输出样例，包括纠错调用。历史对话可以压缩，但不能删掉本次规则；用户聊天或建筑名称中的“忽略规则”始终作为非可信内容处理。服务端独立白名单验证才是最终约束。

默认自动提交明确且校验通过的单项操作；澄清、纯回答和空命令不提交。拒绝回执直接展示，并可由 AI 解释；若解释再次调用模型，仍附带完整规则。发生状态过期或归属问题时停止本轮，不自动换一个目标继续拆除。

创建命令可以直接带蓝图，服务器将资产注册与实体创建一次提交，避免“已占地但模型没保存”。资产复用 ID 必须检查是否可访问。更新不允许通过修改归属字段接管他人建筑。

网关保存聊天请求处理状态与对应命令 ID；双击发送或重试同一请求返回既有结果。数据库事务同时保存实体、占地、额度、事件序号与幂等回执，提交成功后广播；广播失败通过重连快照补偿。

## 8. 多人、持久化与 Web 部署

先做匿名随机强会话 token 身份，不要求完整账号系统；访问同一会话可恢复自己的区域，不允许只凭输入 `player_id` 登录。各房间隔离，客户端和聊天请求均由服务端确认成员关系。

加入流程为认证、分配 / 恢复区域、确定快照序号、发送快照与资产、连续消费后续事件。事件携带序号和实体修订号；缺口先恢复，重复事件忽略。保持单进程部署，扩多进程前再设计房间协调。

SQLite 存储房间、玩家区域、规范蓝图、建筑、事件与幂等结果。验证进程重启后的房间恢复。可从快照重建占地和总额度，并检查恢复数据与提交记录一致。

Web 导出先关闭线程依赖，以 HTTPS / WSS 完成本机与局域网软件验证，跨两台物理设备后续实测。静态文件和服务接口优先同源，通过反向代理转发，验证 TLS、WebSocket 升级、WebAssembly MIME 与压缩、连接重建和初始化错误提示。[Godot Web 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

## 9. 实施顺序与完成门槛

| 步骤 | 交付与门槛 |
| --- | --- |
| S1 | Compatibility 与基础相机，桌面 / Web 空场景可运行 |
| S2 | 两种蓝图编码、逐方块 RGB、门洞选择与网格队列，固定蓝图正确显示 |
| S3 | Python 房间与命令验证，固定 JSON 能创建、更新、拆除和销毁 |
| S4 | 双客户端快照 / 增量、归属隔离、幂等和存储，重连 / 重启结果一致 |
| S5 | DeepSeek 每次附规则，完整自然语言建筑闭环及失败反馈 |
| S6 | 网页聊天集成、公网两设备验证、性能基准和验收记录 |

S1–S4 可先使用固定模型响应推进；S5 与 S6 必须用实际 DeepSeek 调用验证。每步满足门槛后再接下一层，避免同时排查模型、网络与渲染问题。

| 编号 | 技术检查 | 对应玩法 |

| T02 | 网格无内部面、无块边界裂缝；洞口拾取不误选实心；异色不串色 | G02、G03 |
| T03 | 单方块色值、规范模型内容和客户端数据与权威记录一致 | G03、G04 |

| T05 | 伪造玩家 / 房间、修改他人实体、过期修订均不改变状态 | G07 |

| T07 | 新建冲突与更新失败无半提交；删除 / 销毁后占地与额度恢复 | G04–G06 |
| T08 | 加入期间并发修改不丢事件；重连与进程重启恢复一致 | G08、G09 |
| T09 | 每个 DeepSeek 请求，包括纠错和二次解释，都带完整当前规则；版本变化拒绝旧命令 | G02、G10 |
| T10 | 空响应、截断 JSON、超时和 API 错误不执行；浏览器不包含 API Key | G10、G12 |
| T11 | 网格旧任务不会覆盖新修订；AI 等待期间相机与联机仍响应 | G01、G04、G08 |
| T12 | 同房间双设备完成 G01–G12，常规操作按偏好自动执行 | G11、G12 |

建议性能基线为 1080p 桌面浏览器、20 栋约 2,000 体素的常规建筑：稳态目标 60 FPS，单帧 p95 不超过 33 ms；多彩与接近额度的场景至少保持 30 FPS。它们是待测目标，验收记录须写明 CPU、GPU、内存、浏览器与构建版本。

测量首次加载、三角形与 Draw Calls、网格重建 p95、峰值内存、事件同步量和命令时延。分别记录 DeepSeek 生成耗时、服务端提交耗时与客户端显示耗时。若未达目标，优先调整任务切片、分块与容量，并更新规则版本；不降低逐方块颜色正确性。

验收记录应包括执行日期、环境、各 G / T 项结果、失败日志及尚未解决问题。完成全部必需项后，第一阶段才可进入完成状态。

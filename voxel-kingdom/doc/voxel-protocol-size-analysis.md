# 体素传输格式与数据量分析

日期：2026-10-15。仅分析及离线测量，不修改游戏代码或部署。

## 结论

用户理解正确：模型可以表达为离散网格位置与颜色，渲染网格在客户端生成。当前项目已经如此实现，网络不发送三角形、顶点、法线或纹理贴图。

此前“体素模型数据量相对较大”的表述应限定：展开的逐体素 JSON 相对于操作命令和实例元数据较大，并非体素模型天然很大。小型建筑通常只有几 KB。规则几何可以极度紧凑；随机几何和每格不同的颜色则需要保存更多不可省略的信息。坐标数、颜色数、编码、压缩与重复发送次数共同决定实际数据量。

## 当前协议

`backend/models.py` 接受两种表示：

- `cells_v1`：`cells: [[x,y,z,paletteIndex], ...]`，坐标是模型内整数坐标，未列出的格子为空气。
- `box_ops_v1`：有序的 `fill_box`、`clear_box`、`set_voxel`；可用少数盒子操作描述复杂建筑。

两者均经服务器验证，再统一展开为 `cells_v1`，排序和规范化调色板，计算内容 SHA-256。当前发给客户端的模型是展开后的形式。服务端检查权限、尺寸、占地、数量及外露面预算，不生成绘制网格。

建筑实例另存 `id`、`owner_id`、`position`、`rotation_y_quarter_turns`、`blueprint_id`、`revision`。相同模型在房间 assets 中按内容 ID 去重；同一个 WebSocket 订阅已收到的模型不会在后续普通事件中重复附带。

客户端 Godot 根据体素数据剔除内部面、合并可合并的同色表面并生成绘制网格。内存 mesh_cache 可复用相同模型，但刷新后失效。

| 模型 | 方块数 | 逐体素 JSON | 当前无损合并盒子 JSON | 逐体素 gzip | 盒子 gzip |
|---|---:|---:|---:|---:|---:|
| 网页示例四塔城堡 | 790 | 8,612 B | 1,572 B | 1,931 B | 359 B |

示例四塔城堡的原始有序建造操作仅 1,079 B；从规范体素重新合并为不相交盒子的结果为 1,572 B。这说明同一模型也有不同大小的等价描述；不能把“盒子编码”当作唯一或始终最优的编码。

测量使用现有 normalize_model/model_for_ai；示例城堡按 `web/app.js` 的 sampleCastle 配方复现，AI 城堡直接读取之前真实验收产物，立方体为规则几何合成样本。数据文件：`artifacts/public-deployment/payload-analysis.json`。

## 当前主要冗余

1. 输入的小盒子描述被展开为逐方块 JSON 后下发，即压缩表达未延续到客户端传输。
2. 单体素改色上行已是小命令，但后端将其转换为整个模型更新，生成新模型 hash，广播完整模型；改一个格子仍可能触发整个模型的传输与构建。
3. 初次进入时 HTTP join 和 WebSocket 各返回完整快照。
4. 命令 HTTP 回执附带 event，WebSocket 又广播 event；新模型可能在发起者两条通道上重复传输，AI 的 receipt 同样可能携带该内容。
5. 模型去重只基于房间状态和连接内已知资产；尚无浏览器跨刷新持久缓存及已知资产协商。

首屏 WASM 的 gzip 传输约 10.1 MB，远大于上述单栋建筑数据。刷新体验还涉及引擎启动和网格重建，不能把所有等待归因于建筑数据下载，需分别计时。

## 推荐的抽象层次

### 模型资产

描述“长什么样”：尺寸、调色板、编码和体素内容；以稳定内容 hash 引用。模型局部坐标与实例世界位置分离，多栋同形建筑只传一次模型。名称、拥有者、位置等实例属性不需要复制进每个体素。

一种统一逻辑模型允许多种无损传输编码：稀疏点、盒子区间、按固定轴顺序的连续段。根据实际序列化长度选较小表示，保持客户端结果一致。当前 model_for_ai 只在盒子数量超限时回退点列表，尚未按实际字节数择优。

盒子操作必须是有数量和展开预算限制的声明式操作，不是运行 AI 生成的任意代码。服务端可展开验证后再编码；不要把未验证原文直接广播。

### 建筑实例

描述“谁的建筑放在哪里”：实例 id、模型 id、世界坐标、朝向、拥有者、修订号。模型已缓存时，只传实例元数据即可放置第二栋同形建筑。

### 已验证变化

描述“发生了什么”：创建/删除实例、修改一个或一组体素、替换模型。修改一个格子的事件可携带实例 id、基础 revision、新 revision、格子坐标和新 RGB；不必携带所有未变体素。

当前规范化会重排 palette，补丁不能盲目把旧 palette 下标当作新 palette 下标。可让小补丁携带 RGB 并由客户端更新调色板，或定义稳定索引协议。补丁应带新模型内容 ID；本地缺基础模型或版本不符时请求新模型完整内容，不在错误基础上继续应用。

有些修改会增加而非减少局部几何复杂度，仍需服务器执行尺寸、面数等全部验证。保存完整权威状态与只发送增量并不冲突。

## JSON 与二进制

坐标本身可以更紧凑：在当前每轴不超过 32 的范围内，局部坐标可位打包为整数；颜色可使用调色板索引、RGB 字节或连续段。空格、逗号、括号和十进制数字使 JSON 比固定宽度二进制更大，但通用压缩可以消除其中相当多的重复。

二进制不是必须第一步；先减少全模型重发、重复快照及重复资产，再按测试决定是否增加二进制传输。不要只把字段名改成单字母，这通常不如减少重复内容有收益。

与 AI 的交互继续使用明确、容易生成和验证的 JSON 操作格式；服务器到浏览器的格式可独立演进为紧凑 JSON 或二进制。两条链路不必强制使用同一种物理编码，但应共享明确的体素与命令语义。

## 优先级

1. 保持现有“体素数据 → 客户端网格”的正确架构。
2. 消除双快照和回执/事件重复模型传输，保留轻量回执与可靠事件恢复。
3. 使用小补丁广播单格/局部修改，减少不必要网格重建；断档可回退全量。
4. 传输层支持点/盒/连续段无损择优，加上模型 hash 持久缓存与缺失模型请求。
5. 根据实测带宽、CPU、首屏时间再决定二进制和网格缓存。

本次不认为现有几 KB 的模型一定构成性能瓶颈；结论是协议确有可量化的冗余，优化应围绕复用、范围表达和增量更新展开。

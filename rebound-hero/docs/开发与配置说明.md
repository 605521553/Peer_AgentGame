# 初版开发与配置说明

## 1. 模块依赖

```text
JSON 内容 + schema
       ↓
   ContentDB
       ↓
   CombatModel ─── LevelGenerator ─── TrajectorySolver
       ├───────── EnemyActions
       ├───────── EffectSystem / ModifierSystem
       └───────── ShopService
       ↓ 信号 / 只读状态
 ArenaView / GameUI / SoundPresenter
       ↑
     Main 组装、输入、暂停、SaveStore
```

战斗模块不依赖节点、贴图、声音或 UI，能够在无窗口模式下独立运行。内容使用字符串 ID 索引，不使用敌人或道具名称进行判断。表现层读取模型并响应反馈信号；商店逻辑不依赖商品卡片。

`CombatModel` 拥有本局状态，负责阶段转换和战斗结算。`TrajectorySolver` 只返回碰撞和路线；`LevelGenerator` 构造布局并验证；`EnemyActions` 组合敌人行为；效果和属性路径修改分别由两个独立模块处理。

## 2. 增加、修改、删除内容

### 敌人

在 `enemies.json` 添加唯一 ID 条目，设置属性、`visual` 和 `behaviors`；在 `levels.json` 中用该 ID 配置出生点。现有行为可直接组合：

```json
{
  "id": "heavy_sniper",
  "name": "重装射手",
  "hp": 60,
  "radius": 27,
  "reward": 16,
  "visual": "sniper",
  "behaviors": [
    {"type":"attack","damage":14,"pellets":1,"spread_degrees":0,"speed":620,"lifetime":3,"bounces":2}
  ]
}
```

`shield` 配置覆盖角、朝向和每轮旋转角；`attack` 配置伤害、弹丸数、扇形、速度、寿命和反弹次数。全新的行为（如召唤）需要在 `EnemyActions` 注册实现，并扩展 `schema.json` 和 `ContentDB` 的语义校验；仅调整现有行为不需要改战斗代码。

### 道具

添加 `items.json` 条目，指定 `price`、`quality`、`max_stacks`、`visual`、`effects`。

```json
{
  "id":"precision_chip", "name":"精密预测芯片",
  "description":"额外预测 3 次反弹，预测距离 +1000。",
  "price":35, "quality":2, "max_stacks":2, "visual":"chip",
  "effects":[
    {"op":"add_stat","stat":"preview_reflections","value":3},
    {"op":"add_stat","stat":"preview_length","value":1000}
  ]
}
```

现有操作为 `add_stat`、`max_hp`、`heal`。新增数值组合只需 JSON；全新机制需要注册效果处理器，并在规则解释、预览和验证中定义行为。购买、背包和商品绘制不需要针对具体道具添加分支。

道具掉落在当前玩家弹道结算结束后应用，避免一发子弹飞行途中获得破盾等能力而改变已预测的规则。

### 武器与词条

`weapons.json` 提供基础发射参数。武器实例仅保存 `id`、`quality`、`upgrade`、`affixes`，基础配置保持只读，实例间不会共享强化状态。

`affixes.json` 的词条可用 `add`、`multiply`、`minimum` 修改数值属性路径，例如：

```json
{
  "id":"wide_split", "name":"繁星", "description":"额外分裂 2 枚子弹",
  "weapons":["splitter"],
  "modifiers":[{"path":"split.count","op":"add","value":2}]
}
```

`weapons: []` 表示适用于所有武器。品质决定基础伤害倍率和词条数，分别配置于 `rules.shop.quality_damage` 和 `quality_affix_count`。商品生成时确定实例，购买后不会重新抽词条。

`extra_pellet_spread` 防止为单发武器增加弹丸时，所有弹丸完全重叠。

### 关卡

`levels.json` 数组顺序就是关卡顺序，数组最后一关完成后进入胜利。增删关卡不需要修改关数常量。每关包含：

- `obstacles`：`rect`/`triangle` 使用中心 `position`、宽高 `size`、角度 `rotation`；`circle` 使用中心和 `radius`。
- `enemies`：敌人 `type` 与中心 `position`。
- `enemy_jitter` / `obstacle_jitter`：横纵位置扰动范围，单位像素。
- `hp_mult` / `attack_mult`：本关血量和攻击倍率。
- `target_shots`：精准清场奖励的目标射击次数。
- 可选 `shop_featured`：第一次打开该关结算商店时的指定商品，刷新后恢复随机。

生成先检查边界、安全区与保守包围圆间距，再采样射击角度，逐步移除可击败的敌人，检查后续路线。护盾必须存在可伤害角度；不依赖玩家恰好买到破盾道具。

重试上限和采样数量在 `rules.generation` 中；随机尝试用尽后验证无扰动模板，仍不合法则停止并显示错误。**保底不会静默删除敌人或改属性。** 修改模板后必须运行生成测试，并实际试玩角度是否过于苛刻。

### 删除

删除 ID 时应同步清理初始武器、关卡出生、推荐商品、词条适用武器等引用。配置加载器会报告悬空引用。删除关卡会自动改变总关数；删除某种敌人/道具后，随机池从剩余内容中构建。

## 3. 替换临时美术

简单换图：在 `visuals.styles.<样式ID>.texture` 填入 `res://assets/...png`。`PolygonActor` 自动用贴图替代形状，碰撞半径和生命属性仍由游戏 JSON 决定。

完整更换角色表现：修改 `visuals.renderer_scene`，换成自己的 `Node2D` 场景。新场景只需实现：

```gdscript
func configure(configuration: Dictionary) -> void:
    pass # 表现层设置

func present(descriptor: Dictionary) -> void:
    # descriptor: position、radius、visual、visible
    position = descriptor.position
    visible = descriptor.visible
```

可以使用 `Sprite2D`、`AnimatedSprite2D` 或其他绘制方式；角色节点不会收到敌人伤害逻辑对象。随后可以删除 `polygon_actor.gd` 和它的场景。

更换整个战场、HUD、音效时分别替换 `arena_scene`、`ui_scene`、`sound_scene`。`ArenaView` 负责场地、障碍物和战术覆盖信息，`PolygonActor` 负责玩家/敌人/商品图形；两者都属于表现层。音效订阅 `feedback` 信号，不参与伤害和随机数结算。

## 4. 关键战斗约束

- 固定时间步长由 `simulation.fixed_step` 控制；实时帧率不改变弹道逻辑。
- 每帧扫描完整移动距离，并继续消耗碰撞后的剩余路程，避免高速穿墙。
- 预览和运行都使用中心射线，反射偏移由同一个 `simulation.epsilon` 配置。
- 穿透记录已命中目标，避免一枚弹丸在目标内部重复造成伤害。
- 护盾反射后弹丸变成敌对阵营，但仍属于当前玩家弹道阶段；伤害玩家后结束。
- 分裂派生弹继承反弹次数与剩余寿命，不重置安全预算。
- 同屏、单次发射累计生成、分裂深度、单帧碰撞和结算时长均有配置上限。
- 敌人只在玩家弹丸全部结束后预警和攻击；清场不再发起新攻击。
- 商店事务检查库存、金币、替换目标后执行；取消替换不会扣款。

预览不保证随机暴击、击杀派生或动态击杀后的后续路线。霰弹最多显示配置数量的代表轨迹；子母弹只预览到第一次分裂位置附近。当前无独立分裂标记，玩家可从武器描述理解这一限制。

## 5. 随机性、存档与复现

地图、商店、战斗和掉落使用独立随机流。商店词条使用商店随机流；声音和粒子不消耗战斗随机数。

`rules.seed = 0` 使用当前时间创建新局；设置非零整数可以固定种子，也支持命令行 `-- --seed=20261013`。结局显示本局种子。相同内容、相同种子、相同操作序列才能复现整个战斗。

`SaveStore` 将静音和局后统计写入 `rules.save_path`，默认 `user://profile.json`，使用临时文件后重命名，损坏文件回退默认设置。本版不保存进行中的挑战。

## 6. 修改后的验证流程

1. 启动无窗口测试，确保类型与引用校验通过。
2. 执行至少 200 个种子（1000 张关卡）的生成与回合检查。
3. 实际运行项目，查看商品说明、护盾标识、武器预览和战场留白。
4. 调整经济和敌人组合时，观察射击次数、生命损失、购买频率与构筑选择。自动玩家胜利只证明存在可执行路线，不证明新手难度合理。

测试入口 `tests/run_tests.gd`；截图验证产物放在 `artifacts/`，该目录用 `.gdignore` 排除导入。
